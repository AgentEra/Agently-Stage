# Agently-Stage 性能策略：逐命题筛选与证据报告

日期：2026-10-22。基线 Stage 0.3.8，提交 `cfa1db5b9663b4559226dfab4db120adcac22b11`。本轮为研究交付，所有候选都留在本目录，生产包未改动。

## 结论及选择顺序

**目前没有足够证据支持以 Go 或 Rust 重写整个 Stage 调度层。** 这不等于证明原生调度永远没有价值：本轮没有实现语义等价的完整原生调度器。已经测到的收益大部分可以通过提交粒度、存储结构、资源分配和计算边界获得；Stage 本身能够承载多核原生计算。把 Python 回调移交给 Rust 线程驱动没有带来多核扩展。

建议按下列顺序推进后续实现审查。这里“保留”是保留投资方向，**不是已合入生产或已通过完整集成验收**。

| 命题 | 筛选结果 | 应保留的策略与条件 |
|---|---|---|
| H1 提交粒度 | 条件保留，优先级高 | 业务上本来属于一个共同生命周期的细粒度任务，在一个 carrier 根任务内展开；仍需独立句柄/取消/回调的任务不能盲目合并。 |
| H2 carrier 数量 | 淘汰“越多越快”的默认调优 | 维持按实测配置；单个活跃 scope 不会因增加 lanes 自动拆分，多 scope 在本负载下也没有扩展收益。 |
| H3 计算执行边界 | 按负载条件保留 | 纯 Python 粗粒度任务采用显式常驻进程边界；释放 GIL 的计算可用现有线程池。淘汰给细碎 Python 任务盲目加线程/进程。 |
| H4 回放存储 | 条件保留，优先级高 | 长无界历史保留 list 方向；需要有界淘汰时保留分块方向。不能把 Python 分块实现全局替换 deque：小历史明显退化。 |
| H5 通知合并 | 限定场景保留，非默认 | 高扇出同 loop 吞吐场景保留按 loop 合并；跨线程定速尾延迟仅 8 读者配置达预设门槛。其他场景不保留或证据不足。 |
| H6 线程预算 | 条件保留，优先级高 | 慢任务排队会拖累短请求且短请求 SLA 优先时，固定总预算内预留短请求容量；接受长任务总完成时间增加。 |
| H7 契约保持 | 已验证所列边界 | 将正确性当门槛；保留原有 body/settlement 区分、上下文、取消、lag、终态和独立读者语义。 |
| H8 Go/Rust 路线 | 原生计算/批量边界保留；整体重写待证 | 两种语言的原生计算都能经 Stage 扩展；减少跨语言调用次数有收益。没有语言整体胜负或重写必要性的结论。 |
| H9 低迁移替代 | uvloop 条件保留；其他待证 | caller-loop 零等待微任务下 uvloop 达标；Python 3.14 子解释器仅做能力探针，Stage 透明接入失败；free-threading 未测试。 |

优化目标应是有效吞吐、请求延迟、每操作 CPU 成本和可控资源占用。I/O 等待时低 CPU 占用是正常现象；让 CPU 满载本身不是性能成功标准。

## 环境、负载与测量口径

本机 Apple M5 Pro，15 个物理/逻辑核心，48 GiB RAM，macOS 26.5.1 arm64。Python 3.10.21，pytest 8.4.2、psutil 7.2.2、uvloop 0.22.1；Rust 1.99.0、Go 1.27.0。GC 开启，没有绑核、关闭用户服务或控制系统温度。配置、源码摘要见 [main manifest](evidence/main/manifest.json)、[原生重跑 manifest](evidence/native-adapter/manifest.json)，构建记录见 [BUILD.md](BUILD.md)。

所有负载都是合成基础设施测试：**模型调用和网络调用均为 0**。`asyncio.sleep` 只代表可让出执行权的等待，`time.sleep` 只代表占用线程的阻塞等待；不声称测过真实模型、SDK、外部服务或生产并发。

CPU 时间为本进程 user+system；进程池另外加上预热前后存活子进程 CPU 差值。平均核数 = 累计 CPU 秒 / 墙钟秒。它不是系统任务管理器百分比，也不是逐核利用率曲线。子进程列表可能包含 multiprocessing resource tracker；本机 CPU 计数粒度使极短样本的核数失真，不能解读 FFI 18 微秒区间的“1.42 核”。

RSS 是计时后端点值，进程池为父子相加，**不是峰值、独占物理内存或共享页去重值**。`pool_setup_s` 包含工作进程启动及人为的两轮 30ms 预热；`subprocess_wall_s` 包含导入、参考结果计算、池初始化、验证与清理，不是冷请求延迟。不能把它们命名为纯启动成本。

通道回放计时不包含预填，另存 `fill_s`。async 回放包含 `asyncio.run` 创建/关闭 loop 的固定成本，小样本受其影响。定速广播按原定到达时刻计算延迟，消费者处理慢不会把后续请求到达时间推迟；混合请求同样按固定到达时间记录，避免只测“真正开始运行后”的延迟。

## H1：优先减少不必要的细粒度跨线程提交

2000 个任务，零等待或每项 1ms 异步等待。两种 carrier 方式固定使用 carrier，保持预热活跃 epoch；逐任务返回 2000 个 Stage 句柄，批量方式一个根任务内 `asyncio.gather` 产生子任务。

| 配置 | 零等待墙钟 ms | 1ms 等待墙钟 ms |
|---|---:|---:|
| 原生 asyncio | 6.898 | 11.402 |
| caller-loop Stage | 83.648 | 86.195 |
| carrier 逐任务 | 95.617 | 116.591 |
| carrier 批量根任务 | 12.920 | 17.784 |

批量相对逐任务的配对改善为 **85.9% / 82.8%，均 5/5 轮改善**。零等待端点 RSS 从 54.1MB 到 38.5MB。证据候选 ID：`dispatch-9c318a7c2d3f`、`dispatch-3dc342c54e97`。

这支持在合适的生命周期边界减少桥接和句柄创建，不能据此说 Stage 等价工作比 asyncio 慢十几倍：原生 asyncio 对照没有相同的 Stage 生命周期和句柄服务。批量方案也改变独立取消、回调、结果暴露的粒度。补充 [batch-contracts.txt](evidence/batch-contracts.txt) 的两项测试确认 carrier 下 gather 子任务上下文、取消 finalizer 和主体失败后的子任务结算；它不证明任意业务都允许合并。

**决定：保留应用侧共同根任务批量策略；不批准把所有 Stage 调用自动聚合。** 现有 API 即可表达，不必先改语言。

## H2：增加 carrier 数量不是多核计算方案

1000 个任务、1 或 16 个 scope、1/2/4 条 lane。短 CPU 任务在 coroutine 内运行 1000 次 Python 算术；I/O 型为 1ms 异步等待。

| 16 scopes | 1 lane ms | 2 lanes ms | 4 lanes ms |
|---|---:|---:|---:|
| 异步等待 | 39.469 | 43.429 | 43.182 |
| 短 Python 计算 | 111.634 | 115.790 | 113.274 |

实际观察到 16 scopes 分布到 1/2/4 个 loop 线程，CPU 平均仍约 1.0 核。异步等待两种加 lane 配置 0/5 轮改善。单 scope 的全部配置只观察到一个执行 loop，符合 epoch 黏性。

需要正视一个表面反例：单 scope I/O 的 2 lanes 配对改善 12.6%，4/5 轮，达数值门槛。但任务仍在一个 loop 上运行，不能解释为获得第二个执行核心；新增空闲线程、初始化/调度与外部噪声均可能影响该差值。本轮没有隔离这些原因，因此不据此提升默认 lane 数量。

**决定：淘汰“按 CPU 核数增加 carrier 就会更快”的默认策略。** 其他隔离需求、真实多 loop I/O 或 free-threaded 构建仍需独立验证。

## H3：先识别是否释放 GIL，再选择线程或进程

纯 Python 大任务：32 项，每项 100000 次固定 uint64 算术。小任务：256 项，每项 64 次。hash 任务：32 项，每项 50000 轮 PBKDF2-HMAC-SHA256。

| 大任务路径 | 1 worker ms | 4 workers ms | 8 workers ms | 8 workers 平均核数 |
|---|---:|---:|---:|---:|
| Python，直接线程池 | 236.850 | 227.144 | 232.612 | 0.98 |
| Python，Stage+线程池 | 244.164 | 236.079 | 233.565 | 1.00 |
| Python，常驻进程池 | 220.341 | 65.812 | 36.238 | 7.37 |
| hash，直接线程池 | 103.139 | 28.773 | 18.824 | 6.83 |
| hash，Stage+线程池 | 109.863 | 30.664 | 18.674 | 6.67 |

纯 Python 线程数变化均没有达到本轮可靠收益标准。常驻进程 4/8 workers 相对本路径 1 worker 配对改善 69.9%/83.3%，均 5/5；Stage+hash 的 4/8 线程改善 70.8%/83.5%，均 5/5。这直接反驳“只要调度层还是 Python 就不能多核”的普遍判断。

代价明确：Python 大任务 8 进程端点 RSS 262.5MB，线程约 33–34MB；进程池 setup+预热约 185ms。Python 小任务单线程 2.535ms，单进程 16.500ms、8 进程 16.561ms；小任务 Stage 单线程 14.482ms，显示任务管理的固定开销不能忽略。进程扩展不是免费收益。

能力探针 [3.10](evidence/capabilities-310.json) 和 [3.14](evidence/capabilities-314.json) 均证实：进程池直接执行 `pow` 成功，传给 Stage 当 executor 后报 `_contextvars.Context` 不可 pickle。进程性能臂因此通过显式应用边界执行，不冒充 Stage 透明支持。跨进程取消、上下文、错误和序列化需要单独合同。

**决定：保留粗粒度、可序列化的常驻进程计算路径；保留释放 GIL 的线程计算路径；淘汰给细碎 Python 运算盲目加 worker 的策略。** 此处没有实际网络或大型 payload 序列化证据。

## H4：回放算法值得优化，但要按历史规模选结构

将同一 Tunnel 的 `_items` 分别替换为原 deque、无界 list、256 元素块的 Python 分块结构；保持其余生产游标/锁/终态逻辑。完整预填后从头回放。

| 历史长度 | deque sync ms | list sync ms | chunk sync ms |
|---|---:|---:|---:|
| 1,000 | 0.328 | 0.331 | 0.546 |
| 10,000 | 2.970 | 2.697 | 4.631 |
| 100,000 | 80.147 | 26.669 | 46.725 |

100k sync：list 配对改善 65.8%、chunk 34.3%；async：86.720ms → 35.785ms/51.360ms，配对改善 57.0%/39.7%，四项均 5/5。证据 ID：`replay-9ca877f98faf`、`replay-3b660676a80a`、`replay-b5f4716cfd7e`、`replay-909a12eeea86`。

机制上，deque 中间下标访问线性；逐项完整回放的访问总成本可呈二次增长。10k→100k 的原 sync 墙钟增长约 27 倍，list 约 9.9 倍，与该机制一致，但三个点不是独立的渐近复杂度证明。官方复杂度依据见 [SOURCES.md](SOURCES.md)。

反例：chunk 在 1k/10k sync 配对慢 63.4%/53.1%，async 也慢；100k 预填中位数从 deque 44.299ms 增到 chunk 50.527ms，约增加 14%。list 的 10k sync 配对改善 9.8%，没有达到 10% 门槛；1k async 的微小区间易被 loop 固定成本影响，不据此作为主要理由。

list 候选显式拒绝 `max_history`，不能拿它替换有界保留；chunk 清除淘汰引用并删除完整头块，保留至多一个部分头块。随机操作、lag、checkpoint、终态和 35 项既有通道/流测试通过。端点 RSS 在这些规模接近不代表峰值、长时碎片或真实对象保留完全相同。

**决定：保留“长历史 O(1) 定位”的设计方向；无界和有界分开选型。** 尚未测量有界持续淘汰吞吐、真实大对象/长时 RSS、动态切换阈值；不批准全局默认改为当前 Python chunk 原型。

## H5：通知次数减少不保证尾延迟改善

baseline 每个 waiter 一次 `call_soon_threadsafe`；grouped 按 owner-loop 发送一次回调并逐个唤醒 future；local 在当前 owner-loop 使用 `call_soon`，跨 loop 仍 threadsafe。没有丢消息或只保留最新值。

| 场景与指标 | baseline | grouped | local |
|---|---:|---:|---:|
| 同 loop、32 读者、1500 项，无间隔，总 ms | 102.876 | 84.755 | 84.302 |
| 同 loop、8 读者，无间隔，总 ms | 37.238 | 39.258 | 41.710 |
| 跨线程、8 读者、300 项/1ms，P99 ms | 0.410 | 0.389 | 0.553 |
| 跨线程、32 读者、300 项/1ms，P99 ms | 0.623 | 0.540 | 0.609 |

同 loop、32 读者无间隔：grouped/local 配对改善 11.4%/13.0%，均 4/5 轮；grouped 通知中位数 24032→751，CPU 91.697→74.173ms。跨线程 8 读者定速 grouped 的 P99 配对改善 12.4%、4/5，CPU 27.851→16.510ms。保留这两个场景的候选。

但跨线程 32 读者定速 grouped 虽有 25.5% 配对改善中位数，却只有 3/5 轮改善，不达预声明门槛。同 loop 32 读者定速 grouped 的 P99 中位数看似 0.452→0.418ms，**逐轮配对中位却恶化 15.4%，仅 1/5 轮改善**。这说明不能只挑汇总中位数来论证收益。local 的多个定速 P99 也退化。

跨线程无间隔生产者会在 GIL 时间片内形成积压，32 读者 baseline 仅 32 次通知、grouped 1 次，之后读者主要回放已有历史。这不能代表“每条消息都真实唤醒 32 个等待者”，其整体收益不达门槛。

**决定：将按 loop 合并保留为特定高扇出场景候选；淘汰默认全局启用的结论。** local 相比 grouped 是否值得独立维护还没有清晰证据。两个 loop 的正确性测试不等于多 loop 性能测试；公平性、长回调和生产平台尾延迟仍待验证。

## H6：固定总线程预算内隔离短请求，可交换吞吐与延迟

两组总计都为 4 workers。32 个慢任务各阻塞 30ms；100 个快请求按 2ms 固定节奏到达，每个占用线程 0.5ms。shared：一个 4 worker 池；split：慢池 3 + 快池 1。

| 配置 | 快请求 P99 ms | 全部任务墙钟 ms |
|---|---:|---:|
| shared | 259.639 | 280.523 |
| split | 1.278 | 357.720 |

P99 配对改善 **99.5%，5/5**，但全部任务中位完成时间增加 **27.5%**。改善来自队列容量分配，不是增加总线程，也不是发现了更快的 sleep。CPU 平均较低符合阻塞等待性质。

**决定：有短请求 SLA 且慢任务可能堵塞队列时保留预留容量策略。** 若目标只有整批吞吐，共享池更合适。本轮未测长期过载、取消排队任务和动态借用，不推荐把 3+1 写成所有场景默认值。

## H8：原生计算、FFI 粒度与整体调度重写是不同命题

### 原生计算扩展

Rust 和 Go C ABI 实现相同 uint64 递推算法；32 项、每项 5000000 次。直接线程与 Stage 两臂都采用同一普通 Python wrapper，底层 `ctypes.CDLL` 调用在执行原生函数时释放 GIL。只用 native-adapter 数据。

| 原生路径 | 1 worker ms | 4 workers ms | 4 workers 平均核数 |
|---|---:|---:|---:|
| Rust 直接线程池 | 238.650 | 61.207 | 3.84 |
| Rust Stage+线程池 | 242.096 | 63.402 | 3.81 |
| Go 直接线程池 | 240.521 | 61.189 | 3.88 |
| Go Stage+线程池 | 241.251 | 62.994 | 3.82 |

Stage 路径 1→4 worker 配对改善 Rust 73.3%、Go 74.3%，均 5/5。4 worker 下 Stage 相对直接线程的中位墙钟增加约 3.6%/3.0%，说明该粒度的计算可掩盖大部分管理开销。这不是精确“调度占比”，因为两臂包含不同的调度和结算工作。

Python 大任务与原生大任务的 iterations 不同，因此**不报告 Python→Rust/Go 的跨语言速度倍数**。Rust/Go 在这个内核上很接近，也不能外推整套框架语言选择；Go runtime 内存、FFI、安全、打包与运维仍需独立成本评估。

### 跨语言批量边界

50000 项、每项只有 1 次递推：Rust 每项调用 8.889ms、一次 batch 0.018ms；Go 每项调用 10.518ms、batch 0.039ms。配对改善 99.8%/99.6%，均 5/5。batch 在原生侧生成输入并求和，减少 Python 循环、FFI 次数和求和开销；不能把全部差异归为单次 FFI 的纯成本，也不能将 18/39μs 精度区间做严格语言排名。没有真实对象序列化或大 payload。

### 原生线程回调 Python

Rust 线程驱动 64 次同一 Python 回调，每次 20000 次 Python 算术。1/4 worker 分别 97.640/95.979ms，平均约 1 核；配对改善 1.0%、3/5，未达标。GIL 机制与结果一致，但线程创建和回调开销也包含其中。这不是无 GIL Python 的结果。

**决定：保留粗粒度原生计算与批量边界；不保留“换成原生线程驱动就能让 Python 回调多核”的推断。** 如果未来热点是纯原生、无 Python 对象访问的数据结构，Rust 进程内扩展可以作为下一候选；若目标是独立服务，Go 可以比较服务边界。这两种架构建议并非本次已经测出的胜负，更不构成整体重写批准。

## H9：替代 loop 有收益，新解释器不等于透明兼容

caller-loop、2000 个零等待任务：标准 loop Stage 83.648ms → uvloop 58.039ms，配对改善 **32.4%，5/5**；端点 RSS 62.0→63.7MB。原生 asyncio 下 6.898→4.394ms，配对改善 36.2%、4/5。Stage 候选 ID `dispatch-492c56b7e89f`。

**条件保留 uvloop**，范围仅为所测 caller-loop 零等待场景。本轮没有 carrier 内 uvloop、1ms 等待 uvloop、Windows 或完整 Stage suite 在 uvloop 下的验证；不能直接改全局默认 loop policy。

现有 Python 3.14.8 构建 GIL 开启，`Py_GIL_DISABLED=0`。InterpreterPoolExecutor 直接 `pow` 成功，经 Stage 报 `NotShareableError`，因为需要共享 Context.run 等不可共享对象。不存在“直接换 executor 即可”的证据。未获得 free-threaded 构建，不提供其性能数字；本轮也没有 Python 3.10 vs 3.14 全套性能比较。

## 整体重写的决策门槛及剩余不确定性

本轮支持的是局部策略排序。要重新考虑完整调度重写，至少需要真实代表性负载证明：任务粒度、存储、通知和预算优化后，Python 调度仍是端到端主要瓶颈；再让语义等价的原生 prototype 承担同样的上下文、异常、取消、结算、stream、callback、生命周期和集成成本，并比较部署/维护收益。

若调度只占端到端时间比例 `f`，即使它无限快，总加速上限也只有 `1/(1-f)`。本轮没有生产 profile，**没有测得 f**，所以不能用本报告的微基准倍数推导真实模型工作流加速。

局限包括：一台 macOS 工作站、五轮样本、异构核心和外部负载未隔离、若干小区间计时噪声、未调整多重比较、无长期压力/生产 Linux/峰值 RSS 数据；策略组合的相互作用也未测，不能把单项收益相加。性能套件测的是 API 级负载总时间，没有 flamegraph 来精确拆分锁、分配、GIL 等各部分比例。
